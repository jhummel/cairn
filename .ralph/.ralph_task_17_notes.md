# Task #17: Task-counter module src/task-counter.ts

## What was done
Created `src/task-counter.ts` owning a monotonic task-id counter persisted at
`<dataDir>/state.json` as `{ "nextTaskId": N }`.

### Exports
- `reserveTaskIds(dataDir: string, count = 1): number[]` — returns the contiguous
  reserved ids (e.g. `[7,8,9]`). Performs an atomic read → increment-by-count →
  write of `state.json` **inside the shared file lock** from `src/file-lock.ts`
  (lock path `state.json.lock`), using the same temp-file-then-rename atomic
  write pattern as `writeTasksFile` in `tasks-file.ts` (`uniqueTmpPath` =
  `pid + random hex`, self-cleaning on failure). Rejects non-positive / non-integer
  counts.
- `seedNextId(dataDir: string): number` — lazy-seed helper for reuse by `ralph init`
  (task 20). Computes `max(all id values across tasks.completed.json + tasks.json) + 1`,
  floored at 1.

### Behavior details
- **Lazy seeding**: when `state.json` is missing, the start id = `seedNextId(dataDir)`.
  When `state.json` exists, its `nextTaskId` is used verbatim (existing state wins
  over the seed).
- **Cheap id reads** (`readTaskIds`): parses JSON directly and maps `tasks[].id`,
  filtering to finite numbers. Deliberately does NOT use `readTasksFile` (no
  repair/snapshot machinery needed — seeding only wants a best-effort max).
  Tolerates a missing OR empty `tasks.completed.json`/`tasks.json` (returns `[]`).
- **Floor of 1**: brand-new project with no ids anywhere starts at id 1.

## TDD
Wrote `test/task-counter.test.ts` first, watched it fail (`Cannot find module
'../src/task-counter'`), then implemented. Tests cover all required cases:
(a) seed-from-archive max 15 + empty active → 16; (b) single reserve increments by 1;
(c) block reserve count=3 → 3 contiguous ids, counter +3; (d) lazy-seed when
state.json absent; (e) two sequential reserves never overlap; (f) floor of 1 with no
prior ids. Plus: max across both files, existing-state-wins, missing-completed
tolerance, and count validation.

## For the next agent (task 20 — ralph init)

`state.json` without duplicating the max-id logic. Note `reserveTaskIds` already
lazy-seeds on first use, so init writing state.json is an optional optimization, not
a correctness requirement.
