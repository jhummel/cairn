# Task #32 — Thread the resolved dataDir instead of reconstructing paths

## What changed

**`src/index.ts`**
- `setupProjectContext()` line 36: `join(projectRoot, '.ralph')` → `findDataDir(projectRoot)`. This is the *root* of the threading: `RALPH_DATA_DIR` (and therefore every downstream `dataDir` in the CLI, including the one handed to the post-task reviewer) now comes from discovery instead of a literal. Without this the two named sites would have been cosmetic no-ops — everything downstream was still hardcoded `.ralph`.
- summarize action line ~127: `join(projectRoot, '.ralph', 'tasks.completed.json')` → `join(dataDir, 'tasks.completed.json')` using the `dataDir` already in scope.

**`src/post-task-reviewer.ts`** (`spawnPostTaskReviewer`)
- Added `const absDataDir = path.resolve(projectRoot, dataDir)` and built `reviewsDir` from it. Permission rules require an absolute path; resolving against `projectRoot` makes a relative `dataDir` safe too. `path.resolve` on an already-absolute `dataDir` just normalizes it, so real callers are unaffected.
- `reviewFileRule` is now `` `/${reviewsDir}/**` `` instead of `` `/${projectRoot}/.ralph/reviews/**` ``. The allowlist grant and `reviewFilePath` are now derived from the *same* `reviewsDir` variable, so they are structurally incapable of naming different directories. The leading `/` (producing `//abs/path/...`) is the existing convention — kept deliberately, see the comment block.

**`CLAUDE.md`** — the agent-workflow paragraph said the reviewer allowlist covers `.ralph/reviews/**`; now says `<dataDir>/reviews/**` and records *why* the rule must be derived from the resolved dir (silent denial, no error).
